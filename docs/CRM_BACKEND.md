## 역할과 데이터 원본

- Vercel: 기존 홈페이지, `/swatches`, 신규 `/admin/crm`, 서버 API 실행.
- Supabase: 업체/연락처/입장 자격증명/가격 공개 권한/감사·접속 기록.
- GitHub: 소스·스키마·실행 지침. 실제 코드·고객 원본·키는 커밋하지 않는다.
- 상품/재고 및 기존 문의 알림·문의 시트는 이번 이전 범위에 포함하지 않는다. 고객 신원은 DB에서 확인한다.
- Dots: 영업봇 저장소 `handoff/CRM_API.md`, `handoff/CRM_CUTOVER.md`를 따른다. 이 관리자 API는 사람의 로그인용이며 Dots가 관리자 쿠키를 복사해서 사용하면 안 된다. 봇 전용 발송 사전검증/실행 어댑터는 별도 구현 대상이다.

## 관리자

`/admin/crm`에서 회사 이메일로 받은 로그인 링크를 사용한다. Supabase Free 기본 템플릿을 유지하여 추가 SMTP/유료 요금제가 필요하지 않다. URL 토큰은 화면에서 즉시 제거하고 서버가 Supabase 사용자 정보를 검증한 후 HttpOnly 쿠키로 교환한다. 허용된 이메일·이메일 인증·비익명 여부를 서버가 매 요청 확인한다. 공개 회원가입은 비활성화한다. 쿠키는 최대 1시간, 갱신 대신 다시 로그인한다.

업체 등록/수정, 대표 연락처 지정, 코드 확인/발급/재발급/폐기, 업체별 가격 공개/비공개를 제공한다. 가격 변경은 로그인한 소유자의 건별 확인과 감사 기록으로 남는다. 다른 자동 답장·Slack 가격 요청의 승인 요구는 그대로다.

## 코드 의미

코드는 생성된 트랜잭션이 끝나는 즉시 유효하다. 별도 활성 토글이 없다. 기본 가격은 비공개다. 코드 발급은 이메일 발송 허가가 아니다. 기존 4자리 코드를 유지하며 코드 유일성과 한 업체당 유효 코드 1개를 DB가 보장한다. HMAC 조회와 AES-GCM 암호화 저장을 사용하고 일반 목록에는 원문을 내보내지 않는다.

재발급은 기존 코드를 같은 트랜잭션에서 폐기한다. 폐기 여부는 카탈로그/미디어 요청마다 다시 확인한다. 이관 시 기존 세션은 다시 코드를 입력해야 하지만 기존 코드 문자열은 유지한다. 명시적 `비활성` 원본은 폐기 상태로 보존했다. 영업 중지/반송 등 발송 제한은 접속 권한과 별개다.

## 설정

서버 전용: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_PUBLISHABLE_KEY`, `CRM_CODE_HASH_KEY`, `CRM_CODE_ENCRYPTION_KEY`, 기존 `SWATCHES_SESSION_SECRET`. `CRM_BACKEND=supabase`에서만 고객 읽기를 DB로 전환한다. Supabase 선택 후 실패 시 Sheets로 자동 복귀하지 않는다. 모든 CRM 테이블 RLS 활성, anon/authenticated 테이블 및 함수 접근 거부, 서비스 서버만 실행한다.

비밀값의 중앙 원본은 `~/.secrets/lsj/yjtexlab-crm/`이다. API 키를 NEXT_PUBLIC 변수로 노출하지 않는다. DB 관리 토큰은 새 프로젝트 하나에 한정했고 7일 만료다. 브라우저와 Dots에 서비스 키를 전달하지 않는다.

## 이관과 복구

`node scripts/import-crm-sheet.mjs /private/backup.json`은 검증 전용, `--apply`는 전체 스냅샷을 한 트랜잭션으로 넣는다. 기존 source_key를 재실행하면 같은 원본은 건너뛰고 변경된 원본은 거부한다. 원본에는 여러 이메일을 개별 연락처로 분리하고 나머지 필드를 legacy_metadata로 보존하되 코드 원문은 제외한다.

전환 전 마지막 시트 변경 여부를 백업과 비교한다. 실코드 회사명 일치, 가격 비공개 응답, 승인 후 공개, 폐기 후 기존 세션 차단을 확인한다. 원본 전환 후 시트는 조회/보관용으로 두고 쓰기를 차단한다. P열은 소비자 전환과 백업 확인 뒤 숨기거나 제거한다. 전환 후에는 DB 수정분을 조정하지 않고 Sheets로 단순 되돌리지 않는다.
